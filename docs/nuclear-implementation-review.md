## High-impact runtime and architecture gaps

### 1. Critical: authorization, audit scope, and conversation ownership are not one enforced boundary

**Evidence.** `server/_core/index.ts:62–74,81–91,171–183,191–211` registers direct Express configuration reads, MCP calls, Kanban writes, report finalization, and warning acknowledgments without authentication/role middleware in those paths. OAuth registration and tRPC context later at `242–249` do not protect those earlier Express routes. Finalization accepts a request-supplied actor and approval boolean (`173`); `server/agentkit.ts:174–177` checks the boolean before graph promotion, not authenticated reviewer authority.

The connector is protected by bearer authentication, but `server/connect-api.ts:8,91–102` allows non-finalizing `agent_intake` with a look-only token even though `server/ai.ts:139–143,168–170` writes a Kanban item, communications, a conversation, and events. Caller-supplied actor survives at `connect-api.ts:102`. Moves do not require audit scope and `server/kanban-store.ts:26–34` searches all audits by item ID. `server/ai.ts:123–126` retrieves an existing conversation by caller-supplied global ID without checking its audit/owner; `138–143,169` reuses its card and upserts under the newly supplied audit. The helper itself lacks scoped lookup and allows audit reassignment (`server/domain-store.ts:21–24,28–32`).

Graph context is also not audit-bounded: `server/graph-store.ts:45–67` loads the whole graph, walks an undirected connected component, and claims active-audit scope without accepting an audit ID. Shared supplier/person nodes can connect findings across audits. `server/ai.ts:31–39` can combine an explicit graph finding with a fallback portfolio finding. The guided live call omits audit/finding IDs (`client/src/pages/Home.tsx:420`); the endpoint selects another audit with findings when context is absent or the selected audit has none (`server/_core/index.ts:193–203`).

**Minimal safe design.** Enforce one authenticated authorization layer across equivalent REST/MCP paths. Derive actor from the principal; validate audit/tenant membership and item/conversation ownership on every operation and traversal. Treat interim persisted intake as a write, or offer a genuinely non-persisting preview. Reject invalid audit/finding combinations instead of choosing another audit. Graph promotion must require a persisted qualified approval decision, not a client boolean.

### 2. Critical records gap: Kanban attachment bytes are discarded; hashes are not a records vault

**Evidence.** `server/kanban-store.ts:45–48` passes uploaded bytes as `content` to `upsertDomainRecord()`. `server/domain-store.ts:21–24` hashes that content but persists only payload and hash; its table at `17` has no binary column or object location. The attachment payload contains metadata/transcript, not the photo/document bytes. This path therefore cannot retrieve the original uploaded binary from what it stores. It writes the attachment before checking that its card exists (`kanban-store.ts:48–51`), so failure can leave an orphan.

Domain payloads are overwritten in place (`domain-store.ts:24`). Configuration payload, hash, status, and approval are overwriteable at the same version (`server/config-store.ts:41`). The event API inserts rows (`server/event-store.ts:26,36–40`) but explicitly lists client-qualified immutable retention as a **production target** (`57`), not a demonstrated control. Record updates and event appends are separate calls (`kanban-store.ts:21–22,33–34`); event failure can leave an unlogged committed change. Conversation read/modify/upsert is non-atomic (`server/ai.ts:124–126,169`), risking lost turns under concurrent requests.

**Minimal safe design.** Before treating these uploads as evidence, persist and retrieve actual bytes through a governed vault. Bind immutable object/version identity, content hash, owner, custody, retention, and hold policy to each record; verify ownership before writing. Use transactional/outbox consistency, revision concurrency checks, and idempotency keys. SHA-256 is an integrity aid—not WORM, author identity, nonrepudiation, or retention enforcement. Qualify those controls separately.

### 3. High: policy coverage and “grounded” findings overstate the actual evaluation

**Evidence.** `server/policy-runtime.ts:11–26` receives a finding ID but selects the first database audit (`13–16`), concatenates all of that audit's evidence (`17`), checks only the first word of each evidence phrase (`19`), and marks approximately 70% keyword matches `covered`. `rule.evaluator` is echoed, not called. `getControlledPolicyCoverage(auditId)` selects an audit-specific finding but re-enters that first-audit evaluator (`29–35`). `asOf` labels the result; it does not filter historical evidence. This can attribute another audit's evidence to a requested finding and treat descriptive text as control coverage.

`server/regulatory-runtime.ts:7–10` uses the first three sections and first section's summary/risk for every finding without executing a finding-to-requirement traversal. `server/ai.ts:36–38` and `client/src/lib/controlled-config.ts:34–35` construct the same generic path. The alleged document compiler maps the existing rule pack without reading document content (`policy-runtime.ts:46–48`). `server/ai.ts:45–46` calls the first evidence item “weakest” and asserts a supplier substitution plus exactly two records needing revalidation without deriving those facts; that answer is sent to the model as a grounding hint (`69`). The model packet sets `activeAudit` to a finding ID (`58`), substitutes an ontology label for its actual version (`68`), and uses entity IDs as event IDs; `server/graph-store.ts:47,67` does not select event primary keys. A high-severity unresolved-traceability warning is created unconditionally (`ai.ts:83–84`).

**Minimal safe design.** Label existing outputs as keyword/metadata previews, not executable coverage, compilation, or regulatory traversal. Introduce approved deterministic evaluators with pass/fail/unknown/applicability outcomes, evidence IDs, and effective-time queries. Fail unknown evaluators closed. Remove invented deterministic facts and derive warning claims from actual source-linked tests. Carry actual audit ID, ontology/configuration version and hash, and temporal event primary keys in the grounding/run record.

### 4. High: original contracts and reports still conflate Part 21 with Appendix B

**Evidence.** `shared/skills.ts:59` offers `21.51 traceability` and `21.61 nonconforming articles`. `server/evidence.ts:24` embeds `21.51 identification and traceability` and `21.61 nonconforming articles and corrective action` as report criteria. Yet the repository's `shared/regulatory.ts:46–47` identifies §21.51 as maintenance/inspection of records and §21.61 as failure to notify. `shared/policy.ts:40` uses §21.61 as the notification-accountability rule while its regulatory index places the substantive evaluation/notification process at §21.21 (`shared/regulatory.ts:43`).

Candidate contracts improve the separation: dedication/receipt identity references Appendix B VII/VIII (`shared/nuclear-skills.ts:140–146`); nonconformance/CAP references XV/XVI (`178–184`). But adding those files does not correct existing active database contracts or report templates, and the candidates are not approved.

**Minimal safe design.** Obtain qualified nuclear SME review of a provision-level crosswalk separating regulation, Appendix B criteria, guidance, and client interpretation. Correct and version the original interview/report mappings and controlled rows—not just the candidate pack. Preserve superseded versions. Do not substitute an enforcement provision for the substantive §21.21 evaluation/notification basis.

### 5. High: agent routes are strings; candidate clocks are metadata, not durable execution

**Evidence.** `server/agentkit.ts:64–79` retrieves a skill and counts answers; it never dispatches `skill.route`, executes skill-specific evidence tests, or persists an invocation trace. Its count includes optional answers (`68–74`), allowing optional answers to compensate for missing required answers. The simulation constructs tool-call descriptions and marks each phase `Completed` while gates remain pending (`53–61`). “Use skill” passes only a phase (`client/src/pages/Home.tsx:372`) and the guided flow picks its first skill (`408`), not necessarily the selected ID. “Inspect AgentKit route” is a message-only control (`372`). `Home.tsx:442` itself says real AgentKit execution can replace the route pattern later.

The candidate `shared/nuclear-skills.ts:33–43,94–104` defines nuclear route names and clock policies; `shared/skills.ts:27` types clocks as trigger/duration strings. Restored intake maps only generic skills (`server/ai.ts:131–137`) and its context/records (`152–179`) contain no validated discovery/deadline state, timer IDs, working-calendar calculations, or transmission receipts. It does not consume the new clock fields. Bitemporal graph history is not Temporal orchestration or a durable statutory timer.

**Minimal safe design.** Preserve selected skill ID/version, validate each required response/evidence item independently, and label undispatched routes **not executed**. Separate human-reviewed clock policy from deterministic deadline calculation and durable workflow execution. Temporal is a suitable architectural candidate, but requires actual workflows/workers, approved trigger and calendar semantics, restart/replay tests, idempotent escalations, and qualified decision/transmission gates. Do not delegate clock enforcement to LLM prose.

### 6. High: controlled configuration has no end-to-end reviewed activation boundary

**Evidence.** `server/config-store.ts:19–32` permits nullable approvals and multiple active versions per kind/ID. `36–42` can activate or overwrite without reviewer checks or approval events. `45–51` selects the latest updated active row; `61–65` returns every active version. The client reads a catalog of all versions/statuses (`client/src/lib/controlled-config.ts:24–30`) but then re-fetches each item without version/status. A draft-only candidate causes a failed active lookup; repeated revisions can become repeated latest-active payloads. Approval/hash/version envelopes are discarded (`14–17`), success is cached for the session (`20–22,36`), and a failed loading promise is not reset (`23–38`).

The restored admin UI has provider, sync, connector, and workbook controls, not controlled-configuration diff/review/activate/retire controls (`client/src/pages/Home.tsx:615–616`). The safer candidate staging function is not a complete governance workflow. If draft skill rows are present, this loader behavior warrants a negative-state test before claiming they are harmless to the UI.

**Minimal safe design.** Separate runtime active loading from the administrative draft catalog. Preserve version/hash/approval envelopes, deduplicate by a governed active pointer, and fail clearly on ambiguity. Implement authenticated reviewed diffs, immutable revisions, approval events, activation/retirement, and explicit refresh/retry behavior. Do not let draft visibility break operational loading.

### 7. High for data custody: live eCFR ingest and Ollama/local inference are not implemented

**Evidence.** `shared/regulatory.ts:25–33` provides a “Live source link” label, fixed current-as-of date, and URLs—not retrieved authoritative text with a revision manifest. Candidate overlays correctly declare themselves source-link-only (`server/nuclear-config.ts:4–9,25`). Controlled regulatory runtime only reads stored payloads (`server/regulatory-runtime.ts:3–10`); it is not an eCFR synchronization/diff pipeline.

`server/ai.ts:14–22` tracks OpenAI/Anthropic status in process memory; configuring a key checks length and sets a flag but never stores/resolves that key. `keyStored` reflects the flag (`15`). The UI offers those two providers only (`client/src/pages/Home.tsx:567–573`). Actual requests hard-code `claude-haiku-4-5` (`server/ai.ts:72–77,107–111,159–163`); `server/_core/llm.ts:215–224,343–345,405–412` uses the managed API/key. There is no reviewed Ollama provider dispatch or local-processing guarantee. Live packets include portfolio, graph, evidence, and conversation context (`ai.ts:101–111,152–163`). A cyber/export overlay or instruction in a prompt would not itself enforce classification or data egress.

**Minimal safe design.** For eCFR, ingest immutable raw snapshots with source URI, retrieval/effective/revision metadata, content hash, structured provision IDs, change diff, and qualified interpretation/activation gates. For inference, expose requested versus actual provider/endpoint/model and introduce an explicit Ollama adapter with deployment/network controls and model pinning. Enforce classification, authorization, minimized context, and approved egress outside the prompt; fail closed when the chosen local provider is unavailable. Neither source ingestion nor local inference independently establishes compliance.

## Recommended architecture sequence—not a deployment plan

Retain the existing assurance UI and database/graph foundation, but govern four distinct boundaries: **authoritative sources → approved interpretation/rules → durable workflow/human decisions → records vault**, with local/cloud inference as a separately controlled recommendation service. Keep the new nuclear pack draft and outside runtime selection until those contracts are reviewed and executable.

Prioritize authorization/audit isolation and original-binary persistence first. Next qualify source snapshots and the provision crosswalk; replace keyword coverage with evidence evaluators. Then add durable workflow/timers, vault custody/retention, and explicit provider routing. Promote individual capabilities with evidence and blocked states, not an entire “nuclear pack” by label.

The strict acceptance reference requires eight deployed-environment checks (`references/strict-database-graph-agent-acceptance.md:36–47`): fixture/static-ID scans, database integration, ontology rejection, traversal proof, intercepted LLM grounding, guided/chat execution, and empty-state behavior. They were not executed here. Concrete blockers include runtime fixture imports (`client/src/pages/Home.tsx:62–74`), cross-audit fallback/traversal, incorrect grounding IDs/version, and non-executing skill traces. Add nuclear-specific V&V for clocks/calendars, replay/retry, exact provision mappings, negative authorization, conversation ownership, source revision changes, vault retrieval/retention, and human-gated decisions. Until the released environment passes those gates, describe this as a **prototype/architecture candidate with human review required**, not a compliant nuclear assurance system.
